# Output Lifecycle

A system that generates reports needs a rule for when they die, and its
quality gates need to cover the surfaces you actually read.

Both of these sound obvious. Neither happens by default, and the failure mode
is silent in both cases.

## The failure mode

An automated night shift produces reports. Vault hygiene, inbox triage,
knowledge extraction, feedback audit. Each writes a markdown file to the
inbox. Every file is useful the morning it appears.

Nothing consumes them at the same rate. The inbox becomes an append-only log
of things the system noticed and nobody acted on.

The clearest symptom is a triage batch that reads the inbox, decides what
needs attention, and writes its findings as a new file in the inbox. The
system now reports on its own unprocessed output, and the report becomes more
unprocessed output.

## Give generated output a lifespan

Auto-generated reports should expire. Not be deleted, expire: moved to an
archive where they remain greppable but stop competing for attention.

Four properties make this safe enough to run unattended:

**Match on known filename patterns only.** Never expire by age alone. A file
the user wrote themselves stays forever regardless of how old it is. Maintain
an explicit list of the patterns your generators produce and extend it when
you add a batch.

**Move, never delete.** An archive directory bucketed by month keeps history
available. Name collisions get a suffix rather than overwriting.

**Dry-run by default.** Require an explicit flag to actually move anything.
Run it dry the first time and read the list before trusting it.

**Honor a frontmatter escape hatch.** `status: active` or `pinned: true`
protects a file even if it matches a pattern and exceeds the age limit. Parse
only the frontmatter block for this, not the body, or a report that quotes
`status: active` in its text will accidentally protect itself.

Run it before the analysis batches, not after. Triage should read current
material, not archive.

The reaper itself should be deterministic code with no model call. It is
file management, and it should cost nothing.

## Check the scope of your quality gates

If you have an output gate that enforces tone, formatting or privacy rules,
check which surfaces it actually covers.

A gate typically starts life attached to one surface, a chat bot or a CLI, and
its rules get scoped to that agent. Later you add a nightly brief, a digest,
an email. Those are generated by a different code path and the gate never
follows.

The result is inverted from what you want: the interactive surface, where you
would notice a bad response immediately and can just ask again, is strictly
policed. The daily brief you read unedited over breakfast has no checks at
all.

Audit this directly. List every rule in the gate, list every surface that
produces text a human reads, and check the matrix. Expect gaps.

When porting rules to a new surface, verify against real historical output
before enabling them. Run the proposed rules against the last ten files the
surface produced. Zero false positives before it goes live, or you have built
a nightly retry loop instead of a quality gate.

## Close the loop, or admit it is open

A grader that evaluates output and writes its verdict somewhere is only useful
if something acts on the verdict.

Watch for a specific pattern: the same check failing several runs in a row
with no change in behavior. If your grader records history, this is directly
measurable, and it is worth alerting on. Three identical failures means either
the finding is wrong or nothing is listening.

When you find one, resist the urge to build a correction loop first. Check
whether the instruction that produced the output is ambiguous. A grader
demanding something the prompt never asked for is a specification conflict,
not a model failure, and the fix is one sentence rather than a retry
mechanism that costs tokens every night.

Non-blocking quality checks are a legitimate design. Deciding that a warning
should not stop delivery is fine. Just be honest that a warning nobody reads
is not a quality mechanism, it is a log line.
